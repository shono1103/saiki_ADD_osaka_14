# 設定ファイルのスキーマ検証を起動時に入れた話

## この発表のゴール

聞き終わったあと、自分が担当しているサービスの設定まわりを見直して、
「起動時バリデーションを入れてみよう」と思える状態になっていること。

## 一番伝えたいこと

設定ミスは「動かしてみて気づく」ものから「起動時に落ちる」ものに変えられる。

## 前提

- **聴衆の知識レベル**: Node.js / TypeScript は日常的に触っている。Zod は知らない人もいる想定
- **触れないこと**: シークレット管理、環境変数の配布方法
- **決めてほしいこと**: なし（共有が目的）

---

## 構成

### 1. 去年の障害の話 — 4分

**話すこと**

- v2.3.0 のデプロイ後、API が 500 を返し続けた
- 原因は設定値 `timeout` の型が string から number に変わっていたこと
- 本番の設定は `"30s"` のままで、掛け算した結果 NaN になっていた
- 起動はできてしまい、リクエストが来て初めて壊れた

**根拠・数字**

- 影響時間 1 時間 24 分、失敗リクエスト約 48,000 件
- 検知まで 3 分、原因特定まで 26 分

**見せ方の希望**

- P26 縦タイムライン（障害の時系列）
- P29 差分（型が変わった箇所）

### 2. なぜ気づけなかったのか — 3分

**話すこと**

- リリースノートに破壊的変更の記載がなかった
- 型定義はあったが、設定ファイルは JSON なので型チェックが効かない
- 「起動できた = 設定が正しい」と暗黙に信じていた

**見せ方の希望**

- P19 フロー図（設定が読み込まれてから壊れるまでの経路）

### 3. Zod で起動時に検証する — 6分

**話すこと**

- スキーマを 1 ファイルに定義し、起動時に parse する
- 失敗したらプロセスを起動させない（fail fast）
- エラーメッセージにどのキーが問題かを出す
- 既定値もスキーマ側に寄せられるので、コードから分岐が減った

**コード**

```ts
const ConfigSchema = z.object({
  name: z.string().min(1),
  timeout: z.number().int().positive().default(30_000),
  retries: z.number().int().min(0).max(5).default(3),
})

export function loadConfig(raw: unknown) {
  const result = ConfigSchema.safeParse(raw)
  if (!result.success) {
    console.error(formatIssues(result.error.issues))
    process.exit(1)
  }
  return result.data
}
```

強調したい行: `safeParse` している箇所と `process.exit(1)` の箇所

**見せ方の希望**

- P28 コード＋解説

### 4. 導入してどうなったか — 4分

**話すこと**

- 設定起因の障害は導入後 8 ヶ月でゼロ
- ステージングで 3 件、設定ミスを起動時に検出できた
- 副産物として、設定項目のドキュメントがスキーマそのものになった

**根拠・数字**

- 設定起因の障害: 導入前 年 4 件 → 導入後 0 件
- CI で弾けた設定ミス: 3 件

**見せ方の希望**

- P13 KPI カード

### 5. まとめ — 3分

**話すこと**

- 設定は「実行時に壊れる」より「起動時に落ちる」ほうが安い
- スキーマは検証・既定値・ドキュメントを兼ねる
- まず 1 サービスから入れてみてほしい
